I 5 file chiave che ti servono davvero

Se vuoi stare sul solido, senza minimalismo ma senza barocchismi, io metterei almeno questi.

1) contract_manifest.json

È il file radice.
Dice:

  • nome del contratto;

  • versione;

  • draft JSON Schema usato;

  • compatibilità;

  • directory attese;

  • schema principali;

  • vocabolari canonici;

  • policy di versioning.

OpenLineage, per esempio, basa la propria specifica su JSON Schema e insiste molto sul tema schema versioning e su come i cambiamenti di schema richiedano una gestione rigorosa delle versioni.openlineage+1

2) naming_registry.json

È quello che hai in mente quando dici:

“ah, ok, il tal elemento lo devo chiamare così”

Qui definisci in modo centralizzato:

  • entity_kind

  • canonical_name

  • id_prefix

  • singular_label

  • plural_label

  • eventuali alias legacy

  • eventuale regola di naming (snake_case, kebab-case, uri-like, ecc.)

Per esempio:

  • document

  • chunk

  • image_asset

  • image_region

  • use_case

  • procedure

  • table

  • ui_page

  • integration_target

  • batch_job

  • recipe

Questo file è deterministico puro.

3) id_policy.json

Qui stabilisci come si generano gli ID:

  • deterministici da path + ordinal;

  • hash-based;

  • namespace-based;

  • human-readable oppure opaque.

Esempio:

  • doc:manuale_utente

  • chunk:manuale_utente:001

  • img:manuale_utente:img_003

  • ent:procedure:ma27_export

  • recipe:01_dly_management

La regola importante è:
gli ID non si deducono “di volta in volta”.
Si generano sempre con la stessa funzione.

4) enums.json

Qui metti tutti i vocabolari chiusi:

  • entity_kind

  • link_type

  • evidence_kind

  • asset_kind

  • modality

  • processing_stage

  • recipe_status

  • recipe_kind

Questo impedisce che una app scriva ui-page, l’altra ui_page, l’altra ancora screen.

5) schemas/...

Qui c’è il contratto vero e proprio.

JSON Schema è esattamente lo strumento pensato per governare struttura, tipi, vincoli e required fields nei documenti JSON.swagger+1

Come capire se un aggiornamento è “breaking”

Questa è la vera disciplina da introdurre.

Non-breaking change

Esempi:

  • aggiungi un nuovo entity_kind opzionale;

  • aggiungi un nuovo campo non required;

  • aggiungi un nuovo schema extension;

  • aggiungi alias legacy senza cambiare gli ID canonici.github+1

Breaking change

Esempi:

  • rinomini un tipo canonico già usato;

  • cambi il formato degli ID;

  • cambi il significato di un enum esistente;

  • rendi required un campo prima opzionale;

  • sposti concetti tra layer senza compatibilità retroattiva.github+2

Se il cambiamento è breaking, allora devi fare:

  • bump di versione importante del contratto;

  • migration rules;

  • eventualmente adapter o normalizzatore di retrocompatibilità.github+1
